# 加密和混淆管线

魔曰采用密码学主流的 AES-256-CTR 作为核心加密算法，为密文的机密性提供强有力的安全保障。

## AES-256 核心加密

在默认加密模式下，魔曰的密钥与初始化向量(IV)派生如下：

- **密钥生成**：对用户输入的密钥(魔咒)进行一次 SHA-256 哈希，其值作为 AES-256 的加密密钥。
- **IV 生成**：在第一次哈希的结果后附加两个安全随机字节，再次进行 SHA-256 哈希，取结果的前 16 字节作为 CTR 模式的初始化向量(IV)。为了解密时能重构 IV，这两个附加的随机字节会随密文一起保存。

::: warning 密钥流重用风险

默认加密模式下的 IV 仅有 16 bit 的熵。同一密钥重复加密多次时，IV 可能碰撞。

AES-CTR 的密钥流重用(IV 碰撞)会危及密文的机密性，因此敏感数据请启用高级加密模式的 `StrongIV` 功能，并按需启用 HMAC、PBKDF2。

:::

::: tip 为什么削减 IV 长度?

默认 IV 长度的缩减是经过充分辩论和权衡后的工程决策。

完整的 128 位 IV 会显著增加密文长度，导致密文传输效率大幅下降。因此，默认模式下，魔曰选择以更高的密钥流重用风险为代价，减少 IV 的随机字节数，以大幅缩小密文体积。

但这并不意味着魔曰放弃了安全 —— 魔曰保留完整 IV 等高级加密选项，用户可根据安全需求选择启用，以增强安全性，但也会相应增加密文长度。

:::

## 高级加密套件

魔曰支持数个高级加密组件，允许资深用户根据需要增强密文在特殊场景下的安全性。

启用高级加密套件通常会因为附加签名、盐值或强 IV 而使密文长度增加。除 AES-256-CTR 外，下列密码套件受支持，且均可独立开启和关闭：

- **StrongIV**
- **HMAC-SHA256**
- **PBKDF2**
- **TOTP**

### StrongIV

为了尽可能节省密文长度，魔曰默认使用熵为 16 bits(2 字节)的弱初始化向量来派生 AES 的 IV。

开启 StrongIV 后，魔曰将使用密码学安全的随机数生成器产生完整的 128 bits(16 字节)初始化向量。

- **作用**：大幅降低同一密钥下 IV 重复及密钥流重用的概率。
- **副作用**：会将密文增长 14 字节，导致最终的文言文密文显著变长。

### HMAC-SHA256

魔曰默认不对消息进行强完整性验证，仅使用轻量级的[**卢恩算法**](https://zh.wikipedia.org/zh-cn/%E5%8D%A2%E6%81%A9%E7%AE%97%E6%B3%95)(US2950048，ISO/IEC 7812-1)来对解密后的结果做快速校验 (不提供密码学完整性保护)。

打开 HMAC 后，魔曰将使用加密密钥对密文执行 HMAC-SHA256 签名，并将 32 字节的签名附加在密文之后。

- **作用**：验证密文数据的完整性，检测对加密数据的篡改。
- **副作用**：会将密文增长 32 字节。

### PBKDF2

::: tip 提示

启用 PBKDF2 后，由于需要执行十万次密钥哈希迭代，在部分低算力设备上可能会导致短暂的计算卡顿。

:::

默认情况下，魔曰直接将密钥的一次 SHA-256 哈希作为加密密钥。

打开 PBKDF2 后，魔曰会生成一个 16 字节的随机盐值，并使用 PBKDF2 算法对密钥执行 100,000 次哈希迭代(使用 SHA-256 摘要算法)以派生最终的加密密钥，该盐值会被附加在密文之后。

- **作用**：显著增加密钥派生难度，提高离线口令猜测成本，但不能替代高熵密钥。
- **副作用**：密文增长 16 字节。

### TOTP

::: tip 提示

TOTP 并非独立的加密算法，它需要配合 PBKDF2 才能生效。

TOTP 并不能提高密文的机密性，掌握相关密钥者可在有限时间内完全穷举过去一个世纪的所有历史密钥。密文机密性仍然由用户设定的密钥(包括预共享密钥)决定。

:::

TOTP 是 PBKDF2 的附加扩展，允许用户向密文**引入基于时间和预共享密钥的动态盐值**，同时**增加传输效率**：

- 它使用修改后的 TOTP 算法，生成一个 16 位的动态数字(而非传统的 6 或 8 位)。该数字并不直接用于 AES 加密，而是作为 PBKDF2 派生密钥时的“动态盐值”。
- 允许用户自定义 TOTP 步长窗口(对应时间范围为 3 分钟到 1 年)、预共享密钥(BaseKey，默认为主密钥)以及特定的基准时间戳。
- **作用**：按指定时间窗口派生密钥。掌握相关密钥和时间参数者仍可能重算历史密钥，不等同于不可逆的消息过期。由于盐值(TOTP 动态数字)是通过时间推导出来的，因此密文无需在尾部附加 16 字节的 PBKDF2 随机盐值，相比于单纯开启 PBKDF2 可以缩短密文长度。

## 三重转轮混淆

转轮混淆之前的原文是使用 AES 加密后编码而成的 Base64 字符串。转轮混淆的作用是改变 Base64 的字符分布特征，从而在将字符映射为汉字前增加一层混淆层。

```mermaid
flowchart TD
    subgraph Input ["输入处理"]
        A[Base64 字符] -->|解析字符位置| B[字符索引]
    end

    subgraph R_Rotation ["轮转控制 (RoundKey)"]
        K[密钥 SHA-256] -->|取各字节模10| Op[操作数数组 0~9]
        Op -->|根据奇偶性| Rot[计算各转轮轮转偏置]
        Rot -->|步进驱动| R1_Pos[转轮 1 偏置]
        Rot -->|步进驱动| R2_Pos[转轮 2 偏置]
        Rot -->|步进驱动| R3_Pos[转轮 3 偏置]
    end

    subgraph Rotor_Chain ["转轮级联映射"]
        B -->|查原表索引| idx1[原表索引 I]
        idx1 -->|查转轮 1 字符| C[转轮 1 映射字符]
        C -->|查原表索引| idx2[原表索引 J]
        idx2 -->|查转轮 2 字符| D[转轮 2 映射字符]
        D -->|查原表索引| idx3[原表索引 K]
        idx3 -->|查转轮 3 字符| E[转轮 3 映射字符]
    end

    R1_Pos -.-> C
    R2_Pos -.-> D
    R3_Pos -.-> E

    subgraph Output ["输出映射"]
        E -->|获取混淆后字符| F[Rotated Character]
        F -->|文言/传统 Simulator| G[getCryptText]
        G -->|密本查表| H[汉字密文]
    end
```

### 密钥与操作数

1. 对主密钥进行 SHA-256 哈希，得到 32 字节的哈希值。
2. 对这 32 字节的每一个元素执行对 10 取余，得到包含 32 个数字的操作数数组(各元素在 0~9 之间)。

### 轮转规则

加密/解密每个字符时，系统根据操作数数组的当前元素步进旋转转轮，随后将数组索引偏移一位。若偏移到数组末尾则循环重置。
旋转偏置的计算遵守以下规则：

- 如果操作数为 0，将其当作 10 处理。
- **操作数为偶数 (N%2 == 0)**：
  - 第一个转轮(顺序轮)向右轮转 6 位。
  - 第二个转轮(乱序轮)向左轮转 N 位。
  - 第三个转轮(顺序轮)向右轮转 Math.floor(N/2) + 1 位。
- **操作数为奇数 (N%2 != 0)**：
  - 第一个转轮向左轮转 3 位。
  - 第二个转轮向右轮转 N 位。
  - 第三个转轮向左轮转 (N+7)/2 位。

第一个和第三个转轮为顺序轮，第二个转轮为乱序轮(手动打乱)。每次转动的偏置取决于密钥。

### 映射规则

转轮映射采用“字符 -> 索引 -> 字符 -> 索引”的级联查表操作。
设有一个基准字符表(原映射标准字符串)：

```
abcdefg...
```

三个转轮的长度和内容与之对应。转轮旋转相当于改变了该转轮中字符对索引的映射偏移。
对于输入的字符 `a`：

1. 在原字符表中找到 `a` 的索引，得到 `0`。
2. 在旋转后的**第一个转轮**中查找索引 `0` 处的字符，假设为 `b`。
3. 在原字符表中找到 `b` 的索引，得到 `1`。
4. 在旋转后的**第二个转轮**中查找索引 `1` 处的字符，假设为 `d`。
5. 在原字符表中找到 `d` 的索引，得到 `3`。
6. 在旋转后的**第三个转轮**中查找索引 `3` 处的字符，假设为 `i`。
   由此完成了 `a` -> `i` 的级联映射。每次处理完一个字符后，转轮会按照轮转规则步进，因此相同的字符在不同位置会被映射为不同的字符（且该设计允许字符映射为自身，修正了经典 Enigma 机无法映射为自身的密码学缺陷）。

## 加密总流程

```mermaid
flowchart TD
    Start([原始数据 Uint8Array]) --> Checksum[计算并附加 1 字节 Luhn 校验位]
    Checksum --> Compression[自适应压缩 Unishox2 / Gzip]

    subgraph Enc_Block ["加密与哈希处理"]
        Compression --> Adv_Check{是否启用<br/>高级加密?}
        Adv_Check -- 否 --> Standard_Enc[普通加密: AES-256-CTR<br/>附加 2 字节 IV]
        Adv_Check -- 是 --> PBKDF2_Check{是否启用 PBKDF2?}

        PBKDF2_Check -- 否 --> Key_Direct[使用主密钥 SHA-256 哈希]
        PBKDF2_Check -- 是 --> TOTP_Check{是否结合 TOTP?}

        TOTP_Check -- 是 --> Key_TOTP[使用 TOTP BaseKey & Epoch 动态衍生密钥]
        TOTP_Check -- 否 --> Key_Salt[生成 16 字节随机盐并衍生密钥]

        Key_Direct --> Adv_CTR[AES-256-CTR 加密]
        Key_TOTP --> Adv_CTR
        Key_Salt --> Adv_CTR

        Adv_CTR --> HMAC_Check{是否启用 HMAC?}
        HMAC_Check -- 是 --> HMAC_Sig[计算并附加 32 字节 HMAC 签名]
        HMAC_Check -- 否 --> Append_Salt[附加 PBKDF2 随机盐<br/>若无 TOTP]
        HMAC_Sig --> Append_Salt

        Append_Salt --> Append_IV[附加 Strong/Weak IV 并附加高级加密配置位]
    end

    Standard_Enc --> Base64_Enc[Base64 编码并去除 Padding]
    Append_IV --> Base64_Enc

    Base64_Enc --> Magic_Check{插入何种魔数?}
    Magic_Check -->|仅高级加密| Insert_Adv[随机插入 += 标头]
    Magic_Check -->|仅灵活传输| Insert_Flex[随机插入 /=xxxxxxxx 标头]
    Magic_Check -->|同时启用| Insert_Both[随机插入 += 与 /=xxxxxxxx]
    Magic_Check -->|无额外模式| Sim_Input[Base64 编码字符串]

    Insert_Adv --> Sim_Input
    Insert_Flex --> Sim_Input
    Insert_Both --> Sim_Input

    Sim_Input --> Wenyan_Map[三重转轮混淆 & 文言句式载荷字映射]
    Wenyan_Map --> Finished([输出最终汉字密文])
```
